# M9.6b — cluster-info exchange and split execution

**Status:** design proposal, awaiting review. No code yet.

This note fixes the contracts M9.6b depends on, before any code, as
M9.5b-a and M9.6a did. Its first task is not to design the protocol but
to settle a question that determines the milestone's size: the
relationship between the cluster's membership set and the BFT ring's
membership set. That decision comes first because everything else
depends on it.

**Scope.** Two things: how a node learns a neighbour's cluster identity
and size (§13.4's cluster-information tuple, which the draft describes
but does not put on the wire), and what a node does when its own cluster
is due to split (§13.5).

**Out of scope, explicitly.** The trust and identity boundaries
(Outstanding Work item 12) — this note states where cluster membership
sits relative to the BFT ring and stops there. Witness accumulation
(M9.6a, landed). Trust bootstrap (M9.6c). BFT correctness (BFT-A).

---

## §1 — The decision: the BFT ring is independent of the cluster

The question: if a cluster splits while a consensus round is in flight,
does the BFT ring change with it?

Three relationships are possible, and they differ by an order of
magnitude in what 6b has to build.

1. **Live subset.** The BFT ring *is* the current cluster's member set,
   or a quorum-chosen subset that tracks it. A split is then a BFT
   membership change: §5.3.4's quorum-intersection argument, view-change
   certificates, and the checkpoint's signature set all assume a fixed
   membership within a view. Supporting a live subset requires a
   reconfiguration protocol (joint consensus or an equivalent), which
   the draft does not describe. 6b would become a BFT membership-change
   milestone, not a cluster milestone.

2. **Independent.** Ring membership is whatever the ring decided; the
   cluster never enters into it. A split has no BFT consequence at all.

3. **Snapshot-derived, then independent.** Ring members are chosen from
   the cluster's routing-eligible set *when the ring is formed* — by XOR
   proximity to the ring id, which is what `cross_path_consensus`
   already does — and the resulting set is frozen for the ring's
   lifetime. A split changes which peers are candidates for *future*
   rings, not the membership of an existing one.

**Decision: 3.** It is the only one that is both safe under the draft as
written and consistent with the code that exists. It is "independent"
in the sense that matters for 6b: after formation, cluster membership
and ring membership do not interact.

**Consequence: 6b does not touch `bft_driver.rs`.** A ring member that
migrates to another cluster stays a ring member. If it becomes
unreachable, that is a liveness failure the four-phase protocol already
handles — timeouts, view change, `n - f` quorum — not a membership
change. Changing membership to route around an unresponsive node is
what a reconfiguration protocol is for, and this note does not invent
one.

**Why the alternative is rejected.** Under 1, a split would have to
prove that the post-split member set still intersects every prior quorum
in more than `f` members, or run a joint-consensus transition. Neither
is in §5.3.4, and inventing it in 6b would put a consensus-liveness
protocol behind a DHT routing event. The failure mode is quiet: a ring
that loses a member mid-round can stall, and a naive "just drop it"
rule can break the quorum-intersection property the safety argument
rests on.

**Recorded as a spec item.** §5.3.4 should say that a witness ring's
membership is fixed for the ring's lifetime and is not derived from
Coral cluster membership. It is implied by the current text — the ring
is identified by `ring_id`, not by a cluster — but not stated. This is a
text-only revision (S11), recorded in the CHANGELOG's Spec section.

**What would change the decision.** A draft revision that introduces
ring reconfiguration. Then 1 becomes reachable, and 6b gains a BFT
component. Until then, 3 is the contract.

## §2 — What exists, and the four gaps

M9.5b-c part 7 landed the membership derivation: `ClusterHandle`
recomputes on demand from `dht.routing_eligible_records()`, keeps the
peers whose RTT is within `config.rtt_threshold_ms` as
`ClusterView.members`, and exposes `acceptable` (§13.2) and `split_due`
(§13.5). `quip-net`'s `ClusterState` already has the pure decision
functions: `note_rtt_observation`, `should_split`, `choose_split_target`,
`should_merge`, `record_split_attempt`, `clear_split_attempts`.

What is missing is everything that turns those functions into behaviour.

**Gap A — the tuple never reaches the wire.** §13.4 defines a
cluster-information tuple — `cluster_id`, `size`, `ctime`, `signature` —
that a node returns to requests from outside its cluster. The draft
carries it as a figure only. Grep finds no `ClusterInfo` message, no
verb, no codec: it is a documented reply with no documented carrier.

**Gap B — a node never learns a neighbour's cluster.** `ClusterView` is
local. Nothing in `quip-node` records another node's `cluster_id` or
`size`, and no code calls `should_merge`.

**Gap C — a node never acts on `split_due`.** It is computed, exposed
on `ClusterView`, and never read. The cluster id is set once at bind
time (`cluster_id.copy_from_slice(&local_id[..16])`) and never changes;
`choose_split_target` and `record_split_attempt` have no callers.

**Gap D — membership is RTT-only, so a split could not take effect.**
This is the gap that couples the other three. `ClusterView.members` is
"routing-eligible and within threshold". Two nodes that have adopted
different cluster ids would still count each other as members, because
the id is not part of the filter. A split that only changes the local
`id` changes nothing observable until membership is filtered by the
*advertised* id — which requires Gap A and Gap B to be closed first.

That ordering is the milestone: exchange, then filter, then split.

## §3 — Cluster-info on the wire

### The message

A new T0 verb, `cluster_info`, carrying §13.4's tuple verbatim:

```
cluster_info = [
  "quip-v1",
  "cluster_info",
  cluster_id: bytes .size 16,
  size: uint,                ; estimated cluster size
  ctime: uint,               ; cluster creation time, Unix ms
  signature: bytes .size 64  ; by the sending node, §10.1
]
```

It is signed over its own payload, like every other T0 verb. The
receiver verifies against the sender's `NodeId` — the connection's
peer, not a field in the message — so a node cannot speak for another.

### Why a new verb and not a field on an existing response

§13.4 says the tuple is the reply to a level-`i` request originating
outside the current cluster. The request in question is a Coral lookup,
and `lookup_response` has no field that could carry it without changing
its shape. Overloading `spillover` would be worse: it is a failure-path
verb. A new verb is additive, and it is a *naming* of a reply the draft
already mandates rather than a protocol extension.

**No new capability bit.** §13.4 requires the reply of every v1 peer
that participates in the DHT, and `DHT_DISCOVERY` is in the baseline
set. A separate bit would imply the verb is optional, which the draft
does not say.

### Send and receive policy

- Send to every connected peer when the local view changes (`id`, size
  bucket, `ctime`), at most once per `CLUSTER_HEARTBEAT` per peer.
- Reply with our own tuple on receiving a peer's, if ours differs from
  what that peer last told us — a two-message handshake that converges
  without a broadcast storm.
- Store per peer in a bounded map (`NeighbourClusters`). Last write
  wins: the tuple describes the sender's own view, so there is no
  conflict resolution beyond "newer `ctime` for the same `cluster_id`",
  and a peer that migrates simply overwrites.
- Reject `size == 0` and a `ctime` more than the clock-skew allowance
  ahead of `now`. The signature check is the main gate; these are cheap
  sanity bounds.

### Membership becomes id-filtered

`ClusterView.members` gains one predicate: routing-eligible, within
threshold, **and** the peer's advertised `cluster_id` is either unknown
or equal to ours.

Unknown is included deliberately. Before the first exchange every peer
is unknown; excluding unknowns would make a fresh cluster empty and
fail §13.2 forever. The optimistic rule is also the safe one: a peer
that has not claimed a different cluster is treated as a member, and a
peer that *has* is excluded immediately. After a split, each side's
member set is exactly the peers that share its id, without any
transport-level partition.

**The filter is a new predicate, not a change to routing eligibility.**
`is_routing_eligible` keeps its transport meaning — `NatDirect` or
`NatRelayed` — because that is what its existing callers need and what
M9.5b-a established. 6b adds
`is_cluster_member(peer, local_cluster_id)`, defined as
`is_routing_eligible(peer) && advertised_id(peer) == local_cluster_id`,
and the two consumers that care about cluster shape consult the
conjunction: `ClusterHandle::recompute` and `dht_router_task`'s mesh
routing. `routing_eligible_peers`, `routing_eligible_records` and
`DhtHandle::closest_to` keep their current meaning.

The alternative — adding the conjunct to `is_routing_eligible` itself —
would make one name return two different sets depending on which layer
asked, and it is the shape M9.5b-a deliberately avoided when it
separated routing eligibility from physical connection existence. The
new conjunct belongs at the call sites that mean "member", not in the
predicate that means "reachable".

**Record is not member.** The neighbour record is written
*unconditionally* after the signature verifies; the id filter is applied
at **read** time — in `ClusterHandle::recompute` and in the router —
never at write time. A neighbour that announces a different id must stay
in the record, because the record is a fact about what was announced and
the filter is what changes when the local id changes. Filtering at write
time would require re-verifying the record after every local-id change,
which is the bug class the filter exists to prevent.

So the inbound handling of `cluster_info` has three steps in this order:
parse (with the capability check, inside `parse_inbound`), verify the
signature against the announced `node_id`, and record it. Filtering is
step four and it happens on read, not on receipt.

## §4 — Split execution

### Trigger

`split_due` — the p90 RTT has been over threshold for more than
`heartbeat * 3`. Any within-threshold observation clears the timer
(`note_rtt_observation`), so the trigger is persistence, not a single
bad sample.

### Choosing a branch

§13.5's algorithm is a `get(hash(cid^N))` to find the cluster center,
then an RTT measurement to it. 6b keeps the decision and simplifies the
discovery:

- The cluster id is the low 16 bytes of the local `NodeId` at bind time.
  §13.5 derives `cid^N = hash(cid)`; 6b defines `hash` as SHA-256 over
  the 16-byte id, truncated to 16 bytes, and `cid^F` as `cid^N` with bit
  0 of the first byte flipped. Both are computed locally.
- The center is the connected, routing-eligible peer closest by XOR to
  `hash(cid^N)`. (See §6's limitation: there is no address book beyond
  connected peers, so a real DHT lookup for the center is deferred.)
- `rtt_to_center` is that peer's recorded RTT sample.
- `near_acceptable` / `far_acceptable` are local verdicts: at least one
  peer advertises the candidate id, our RTT sample to it is within
  threshold, and its advertised `size` is at least `MIN_CLUSTER_SIZE`.
- `ClusterState::choose_split_target(rtt_to_center, near_acceptable,
  far_acceptable, config)` returns `JoinNear`, `JoinFar` or
  `CreateNew`.

### Applying it

1. `record_split_attempt(&config)`. If it returns `Err` (more than
   `MAX_SPLIT_ATTEMPTS`), take `CreateNew` regardless.
2. `ClusterHandle::migrate(new_id, now)`: a new `ClusterState` with the
   new id, `ctime = now`, `size` recomputed from the routing table, and
   `split_attempts` cleared on success.
3. Announce `cluster_info` to every connected peer.
4. Recomputed membership now excludes peers that kept the old id.

The split is **local and uncoordinated**: every node evaluates the same
inputs but may pick a different branch, and the partition is the union
of their choices rather than a decision made by one node. That is what
§13.5 describes — each node decides which cluster it joins — and it is
why the id-filtered membership in §3 is load-bearing.

### A new cluster id without a random source

`CreateNew` needs an unpredictable id. `quip-node` has no `rand`
dependency and `quip-core` is `no_std`, so 6b derives it as
`SHA-256(local_node_id || now_ms || split_attempts)[..16]`, using the
same hasher the CID code uses. It is not cryptographically random, but
it is unpredictable to a remote peer and collision-resistant enough for
an id that acceptance re-validates anyway. Recorded in §7.

## §5 — `acceptable` and `split_due` are different predicates

They are easy to conflate because both are booleans on `ClusterView`, so
the note states the distinction because 6b's code depends on it.

- `split_due` answers **when**: the RTT p90 has been over threshold long
  enough. It is persistence. Any within-threshold observation clears it,
  so a transient spike never splits a cluster.
- `acceptable` answers **how good a candidate is**: §13.2's acceptance
  test. `choose_split_target` takes two of these — near and far — and
  uses them to choose a branch.

The current cluster's `acceptable` is **not** an input to the split
decision. It is an output for observability. In practice `split_due`
implies it is false, because the same p90 drives both, but the code does
not rely on that implication and 6b does not either: gating the split on
`!acceptable` would add a second condition that can only disagree with
the timer during the window in which a recovery has just been observed,
and in that window `split_due` is already false.

What `acceptable` *is* used for: `near_acceptable` and `far_acceptable`,
which are verdicts on the candidates, not on the current cluster.

Put in the shape the code must follow: two predicates, computed at
different times on different inputs, neither gating the other.

- `split_due` is a property of the **current** cluster's history — how
  long the p90 has stayed above threshold.
- `acceptable` is a property of a **candidate set** at the moment it is
  evaluated — given these peers and these RTTs, is this cluster
  acceptable?

The consequences are not defects. A cluster can be `split_due` while
`acceptable` is true (the RTTs came down but the timer has not yet been
cleared), and it can be `acceptable: false` while `split_due` is false
(one bad sample, not yet persistent). Neither state is an error, and 6b
must not add a cross-check that treats either as one.

## §6 — What lands in the 6b commit

**`quip-net`**

- `cluster.rs` — `ClusterInfoAnnounce`: §13.4's tuple plus the sender's
  signature, with `to_bytes` / `from_bytes` / `signing_payload` /
  `verify`. `ClusterInfo` itself stays unsigned, because it is a decision
  input, not a wire object.
- `message.rs` — `Message::ClusterInfo`, its dispatch arm, verb
  `cluster_info`, `required_tier() == Tier::Ctrl`, and
  `required_capability() == DHT_DISCOVERY`. The new arm is what makes
  the verb work with the Pre-6b capability gate: no change to
  `dispatch_inbound`, `classify_inbound` or `apply_inbound` is needed
  beyond adding the variant.
- Tests: codec roundtrip, a forged signature rejected, the capability
  requirement.

**`quip-node`**

- `cluster.rs` — `NeighbourClusters` (bounded, keyed by `NodeId`),
  `observe_cluster_info`, the id filter in `recompute`, `migrate`,
  `evaluate_split`, and `new_cluster_id`.
- `tasks.rs` — `InboundAction::ClusterInfo`, with
  `InboundOptions::serve_cluster_info` true in NAT, discovery and
  steady, false in handshake and datagrams. The handler verifies, stores
  and replies. Adding a verb is now a variant plus a flag, which is what
  Pre-6b was for.
- A `cluster_task`: a `CLUSTER_HEARTBEAT_S` tick that recomputes the view,
  announces on change, and evaluates a split. It sends through
  `DhtHandle::publish_cluster_info`, which reuses the existing outbound
  router with an untargeted mesh verb.
- `lib.rs` — spawn the task in `bind_with_store`; `Node::cluster_view`
  already exists, and `Node::neighbour_clusters()` is added for tests.

**Tests**

- Membership: a peer with a known different id is excluded; an unknown
  peer is included; a peer that changes id is excluded on the next
  recompute.
- Split decision: with a `ManualClock`, drive the p90 over threshold for
  more than three heartbeats and assert `split_due`; then assert
  `JoinNear` / `JoinFar` / `CreateNew` for the three candidate-verdict
  combinations.
- Integration: a small mesh with a forced-low threshold; assert that a
  split changes the cluster ids and that the member sets partition along
  the ids, with the exchanged tuple as the only input that makes it
  happen.

**CHANGELOG** — M9.6b row to `landed`, a section, tag-index rows, and
Spec item S11 (§5.3.4 states ring membership is fixed and independent of
cluster membership).

**Not in this commit.** Merge (§13.4) — the tuple and the store make it
possible, but it is a separate decision and not part of "split
execution". Sloppy replication (§13.5) — a lookup optimisation with no
requirement behind it in this implementation.

**Center selection is a heuristic in 6b.** §13.5 asks for the node
closest to `hash(cluster_id)` in the DSHT. 6b uses the closest
*connected* routing-eligible peer, because the node has no address book
beyond connected peers — Coral returns `NodeId`s, not addresses. In a
two-node network the two coincide; in anything larger, the center is a
function of what is connected rather than of what exists, which is
exactly the property a split is meant to change. A real lookup is
deferred to **M9.8**, the milestone that introduces a peer address book.

## §7 — The six questions, answered

1. **Which §13 verb carries `ClusterInfo`?** A new T0 verb
   `cluster_info`, carrying §13.4's tuple plus a signature. No existing
   verb has a field for it, and adding one would change a message that
   other code already depends on.
2. **How do neighbours exchange cluster ids?** Announce on view change,
   at most once per heartbeat per peer, and reply on receipt when the
   tuples differ. Stored per peer in a bounded map.
3. **What is split migration's protocol?** §4: the timer opens the
   decision, `choose_split_target` picks a branch from the candidates'
   acceptability, the node migrates its id, announces, and filters
   membership by the advertised id. Local and uncoordinated, as §13.5
   describes.
4. **How are `acceptable` and `split_due` both used?** §5: `split_due`
   is the trigger (persistence); `acceptable` is a verdict on the
   *candidates*, used to choose near/far/new. The current cluster's
   `acceptable` is an output, not an input.
5. **What happens to BFT ring membership if a split lands mid-round?**
   Nothing. §1: a ring's membership is frozen at formation; a split
   changes future candidate sets only.
6. **What is the relationship between the cluster and the BFT ring?**
   Snapshot-derived at formation, independent thereafter. **6b does not
   touch `bft_driver.rs`.**

## §8 — Open questions for review

1. **Hash-derived cluster id.** `SHA-256(node_id || now || attempts)` is
   unpredictable to a peer but not uniformly random. A `rand`
   dependency would be a new decision for the workspace; the hash is
   enough for an id that acceptance validates. **Recommendation: hash.**
2. **`hash` in §13.5 is undefined, so 6b's reading is provisional.**
   The draft writes `cid^N = hash(cid)` without defining `hash`. 6b
   reads it literally — SHA-256 over the 16-byte id, truncated to 16
   bytes — because the draft names a function it does not define. The
   competing reading treats the id as already hashed and uses it
   directly. **§13.5 should be edited to define `hash`; if it defines it
   differently, the implementation changes.** This is the S9/S10 pattern
   applied to a Category 3 gap: the code makes a choice, the draft
   ratifies or corrects it, and the CHANGELOG records which state is
   current. Until the draft says, 6b's reading is provisional.
3. **Unknown-id peers counted as members.** Excluding them deadlocks a
   fresh cluster; including them is optimistic and self-corrects on the
   first exchange. **Recommendation: include.**
4. **Center discovery uses connected peers only.** See §6: the center is
   a function of what is connected, not of what exists. Recorded as a
   follow-up for the milestone that introduces a peer address book, not
   a 6b requirement.
5. **Size cross-validation.** §13.6 says nodes SHOULD cross-validate
   advertised sizes. 6b stores them as given. If a lying neighbour can
   steer a split by inflating its size, that is a real vector;
   **recommendation: record it, do not solve it in 6b**, because the
   merge decision is where it bites and merge is out of scope.
6. **Uncoordinated split.** Two nodes can pick different branches and
   partition; that is the design, but it means a split is not atomic and
   a cluster can fragment into more pieces than §13.5's two. Worth
   stating in the section, not solving.

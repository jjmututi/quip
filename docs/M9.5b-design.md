# M9.5b Design: Peer Lifecycle, Routing, and Cluster Membership

**Status:** Proposed contract, verified against the protocol specification and existing implementation. Ready for review as the authoritative contract for M9.5b.

**Purpose:** Establish the shared contracts required for NAT-driver and cluster merge/split integration.

## 1. Peer identity and generation

Introduce a `PeerSlot` abstraction identifying a particular connection generation for a logical peer.

- `NodeId` identifies a logical node.
- `PeerSlot` identifies its active connection generation.
- Events must be associated with the generation that produced them.
- Events from an obsolete generation must not mutate the current routing or cluster state.

Evaluate `quinn::Connection::stable_id()` as the generation identifier, verifying its guarantees against the project's pinned Quinn version. If it does not satisfy the required uniqueness and lifetime semantics, use an explicit per-peer generation counter.

## 2. Peer lifecycle

Define a shared lifecycle vocabulary:

- `Connecting`
- `Established`
- `NatDirect`
- `NatRelayed`
- `Failed`
- `Closing`

`Established` indicates an established QUIC connection. `NatDirect` and `NatRelayed` indicate the relevant NAT/connection-flow outcomes.

Lifecycle transitions must be explicit and generation-scoped.

**Connection lifecycle is one of three independent dimensions.** The other two are witness verification (`Pending` / `Verified`, produced by the §16 discovery phase) and application trust (`Unknown` / `Trusted` / `Untrusted` / `Revoked`, produced by `TrustPolicy`). A peer can be `NatDirect` with witness status `Pending` and application trust `Unknown`; none of those combinations requires a new lifecycle state.

### 2a. Lifecycle transitions

Verified against `quip-net/src/establishment.rs` and `quip-node/src/lib.rs`:

```
Connecting  → Established
Established → NatDirect | NatRelayed | Failed
NatDirect  ↔ NatRelayed
NatDirect | NatRelayed → Failed
Any nonterminal state  → Closing
Failed, Closing → terminal for this PeerSlot
```

Recovery after `Failed` or `Closing` creates a new `PeerSlot`. Delayed events from the previous slot cannot restore its former state.

**Discovery failure does not produce `Failed`.** `ConnectionFlow::on_discovery_failed()` transitions to `Ready(Pending)`, which the node treats as a successful establishment. `ConnectionFlow::poll()` can produce `Failed(DiscoveryTimeout)`, but the node's discovery runner handles its own five-second timeout by falling back to `Ready(Pending)` first, so the flow-level timeout is not reached in practice. A peer whose NAT path is established but whose witness discovery did not complete remains at `NatDirect` or `NatRelayed`; its witness status is `Pending` and its application trust is whatever `TrustPolicy` says.

A path change between `NatDirect` and `NatRelayed` must not implicitly recreate the peer connection.

## 3. Routing-table contract

The routing table is keyed by logical `NodeId`, with each active record associated with its current `PeerSlot`.

Physical connection existence and routing eligibility are distinct.

The NAT integration track owns setting routing eligibility when the peer reaches an eligible direct or relayed state. The lifecycle and cleanup path owns clearing eligibility on failure, closure, or replacement by a new generation.

The implementation must prevent stale connection generations from remaining eligible after reconnection.

## 4. Cluster-membership contract

**Default: follow protocol specification §13.2.**

Cluster membership is a subset of known routing-table peers. A peer being known or connected does not, by itself, establish cluster eligibility.

**§13.2 requires cluster acceptance to be based on RTT.** At least 90% of nodes in the cluster must be within the cluster's RTT threshold. The recommended acceptance procedure samples at least 20 nodes, measures their RTTs, and checks the 90th percentile. `ClusterState::is_acceptable` in `quip-net/src/cluster.rs` enforces this by returning `false` when fewer than `ACCEPTANCE_MIN_SAMPLES` (20) samples are supplied.

**The sample requirement binds the acceptance decision, not individual members.** The §13.2 sampling procedure is the test a node applies when deciding whether a cluster is acceptable. It does not require every cluster member to independently carry a 20-observation history.

Cluster membership must therefore be derived from both the relevant peer state and the specified cluster acceptance test. The routing table and cluster member set must not be assumed to be identical.

The implementation must define how membership is recalculated when RTT observations change, peers reconnect, or cluster membership changes.

## 5. RTT observations

Expose `ConnectionDriver::rtt() -> Option<Duration>` in `quip-net`, reading the RTT statistic from the underlying Quinn connection. The return is `Option` because the transport's RTT statistic is not necessarily populated before the first sample is taken.

RTT-dependent cluster decisions must use valid observations and the sampling rules required by §13.2.

**Missing RTT means not yet eligible.** A peer with no RTT observation cannot positively satisfy the acceptance test. Missing observations must not be represented as zero or silently treated as valid samples.

`ClusterState::is_acceptable` already enforces `ACCEPTANCE_MIN_SAMPLES`. The implementation must consistently exclude missing observations and reject insufficient valid samples. A peer with missing RTT data must not independently satisfy the cluster acceptance test.

## 6. NAT session coordination

Reuse the existing deterministic `derive_session_id(local, remote)` implementation in `quip-node`.

Both endpoints must derive the same session identifier from the same logical peer identities, regardless of endpoint ordering.

Session identity and connection-generation identity are separate concerns unless the NAT protocol explicitly specifies otherwise.

Add a test proving that both endpoints derive identical session IDs for the same peer pair.

## 7. Integration gates

Before parallel NAT and cluster implementation begins:

1. ~~Verify the membership and RTT rules against §13.2.~~ **Done.** §13.2 requires 90th-percentile RTT at or below threshold with a minimum 20-sample procedure; the sample requirement binds the acceptance decision, not individual members.
2. ~~Confirm the `ConnectionFlow` failure semantics.~~ **Done.** Discovery failure yields `Ready(Pending)`; it does not require a lifecycle variant.
3. Agree on `PeerSlot` ownership and generation identity.
4. Freeze the lifecycle transition rules.
5. Define routing-table record semantics and cluster-member identity.
6. Define how routing eligibility changes with NAT and lifecycle events.
7. Implement and test the shared types and RTT accessor.

The NAT and cluster tracks may proceed independently only after gates 3–7 are closed and the contracts are available in code.

## 8. Acceptance invariants

- Every cluster member has a corresponding current routing-table entry.
- Every cluster member satisfies the agreed lifecycle eligibility conditions.
- The cluster-joining decision passed the §13.2 acceptance test using the required number of valid RTT observations.
- Missing RTT observations do not count toward the required sample minimum and do not independently satisfy the acceptance test.
- Events from stale peer generations cannot mutate current membership or routing eligibility.
- Disconnect and reconnect leave routing and cluster state consistent.
- A peer with `Pending` witness status and `Unknown` application trust may still be a cluster member if it satisfies §13.2; the three dimensions are independent.
- NAT session identifiers agree across endpoints.
- Multi-node tests exercise NAT establishment, cluster merge/split, reconnect recovery, and Coral routing.

## 9. Scope and authority

This document defines node-level integration contracts; it does not amend the wire protocol.

The protocol specification takes precedence over this note. Where implementation details, existing tests, or the proposed transitions conflict with the specification, resolve the discrepancy before freezing the affected contract.

**Completion gate:** M9.5b is complete only when the integrated behavior passes the acceptance tests and the implementation, specification references, and changelog agree.

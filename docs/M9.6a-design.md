# M9.6a — Witness accumulation and issuance

**Status:** design, reviewed and corrected. No code yet.

This note fixes the contracts M9.6a depends on. It is the first
milestone since M9.5b-a whose shape is not already frozen in the
draft or an earlier design document, so it lands as a note before it
lands as code.

**Scope.** This note covers *accumulation*: how a running node
collects `WitnessStatement`s, where they live, what the Coral
responder returns for a `coral_lookup`, and how a node issues its
own statements. It does *not* cover trust bootstrap (how a fresh
node acquires its first witness statement in a network that has
none) — that is deferred, and it needs its own note because the spec
does not describe it.

**Out of scope for this note, explicitly.** Cluster-info exchange
and split execution (deferred from M9.5b-c part 7); the trust-policy
machinery itself (`TrustPolicy` and its four levels); the flow's
existing per-connection KT computation (`ConnectionFlow`'s
`RemoteState.witnesses`), which stays as-is except where §2a seam 2
and §7 name it.

---

## §1 — What exists

`quip-node/src/discovery.rs` wraps `quip_net::discovery::WitnessDiscovery`
in a `DiscoveryHandle`. The handle is the node's Coral client and
server: the client starts a lookup for each peer during §16
establishment and ingests the response; the server answers inbound
`coral_lookup` and `spillover` requests. Today the server answers
with an empty ring — `respond_to_lookup` returns a `LookupResponse`
with `values: Vec::new()` and zeroed `value_hash` per path — because
the node holds no `WitnessStatement`s.

`quip-net/src/establishment.rs` holds a per-connection
`RemoteState.witnesses: BTreeMap<NodeId, WitnessStatement>`. It
exists to compute the connection's `KtStatus` (`Verified` for 4+
non-expired witnesses). It is per-connection by construction.

`quip-node/src/trust.rs`'s `TrustPolicy` records a `StoredClaim` per
peer (the claim, a first-seen time, the decision time, the level).
It exists for TOFU pinning and for the four-level policy axis.

None of these is a node-wide witness store.

**Correction — the flow's witness map is never populated.** It is
worth being precise about what "populated" means here, because the
rest of this note depends on it. `ConnectionFlow::on_message` is the
only code that writes `RemoteState.witnesses`, and it is called
*only in `establishment.rs`'s own tests*. In a running node, inbound
frames during the NAT phase go to the NAT driver (`run_nat_phase`)
and during the discovery phase to `handle_discovery_event`, which
routes the Coral verbs and ignores `AnnounceWitness`. So
`RemoteState.witnesses` is empty in production, `compute_kt_status`
always returns `Pending`, and **`Ready(Verified)` is unreachable
today** — not because the node holds no witnesses, but because
nothing feeds the flow's witness map. M9.6a has to close that gap as
well; see §2a seam 2.

## §2 — The WitnessStore

A new module `quip-node/src/witness.rs` holding a `WitnessStore`,
keyed by `(subject: NodeId, witness: NodeId)`.

The store is *data*. It does not orchestrate; it does not decide
policy; it answers three questions:

1. "What valid statements do I hold for `subject`?" — used by the
   responder.
2. "Have I seen a statement from `witness` about `subject`?" — used
   to dedupe on ingest.
3. "When did I first see a claim for `witness`?" — but only by
   consulting §2.5's `ClaimLog`; the store does not own that fact.

Shape, roughly:

```rust
pub struct WitnessStore {
    inner: Mutex<WitnessInner>,
}

struct WitnessInner {
    statements: BTreeMap<(NodeId, NodeId), WitnessStatement>,
    by_expiry: BTreeSet<(Timestamp, NodeId, NodeId)>,
}
```

`ingest(statement, now)` inserts if the statement is valid (subject
and witness are set, `valid_until > now`) and either no statement
exists for the pair or the new one has a later `timestamp`. It is
idempotent: a replayed statement is dropped.

`statements_for(subject, claim_log, now)` returns every statement for
`subject` whose `valid_until > now` *and* whose witness has a
first-seen claim at least `WITNESS_FIRST_SEEN_SECONDS` in the past
per the `ClaimLog`. It caps at `WITNESS_COUNT`.

The store never writes to `TrustPolicy`. The trust policy never reads
from the store. Both read the `ClaimLog`.

### §2a — Where accumulation happens: three seams, not one

`AnnounceWitness` arrives on T0. It is the *only* witness-carrying
verb. Today the *only* handler in the workspace is
`ConnectionFlow::on_message` (`establishment.rs`), which stores into
`RemoteState.witnesses` for KT computation — and, per §1, is never
called in production. The peer task's steady loop (`run_peer_loop` in
`tasks.rs`) has no `AnnounceWitness` branch at all: it falls through
all four inbound branches (`try_serve_relay_discovery`,
`dht_result_from`, `is_coral_verb`, `try_auto_serve_pins`) and
surfaces as a `NodeEvent::Message`.

The lifetimes are disjoint:

- Before the flow reaches `Ready`, only the flow reads inbound
  frames. `run_peer_loop` does not exist yet.
- After the flow reaches `Ready`, only `run_peer_loop` reads inbound
  frames. The flow has returned and is not advanced further.

So accumulation needs a seam in **three** places.

**Seam 1 — store ingress during establishment.** Inside
`run_discovery_phase` (`tasks.rs`). Every inbound `AnnounceWitness`
the establishment loop sees is decoded, verified, and passed to
`witness_store.ingest(...)`.

**Seam 2 — requester-side KT wiring.** Inside `run_discovery_phase`
as well. The same decoded statement must reach `ConnectionFlow` —
`flow.on_message(Message::AnnounceWitness(stmt), now)` — so
`compute_kt_status` counts it. Today nothing feeds the flow, so this
seam is what makes `RemoteState.witnesses` non-empty and
`Ready(Verified)` reachable at all. Without it, §1's correction
stands and §5 cannot pass: the responder can return four statements
and the flow will still report `Pending`, because it counts a map
nothing fills.

Seam 2 is *not* a mirror of seam 1. Seam 1 fills the node-wide store
for the responder; seam 2 fills the per-connection flow map for KT.
Both read the same decoded statement, and neither substitutes for the
other.

**Seam 3 — store ingress in the steady loop.** Inside `run_peer_loop`
(`tasks.rs`). A new inbound branch, placed **first** — before
`try_serve_relay_discovery` — decodes `Message::AnnounceWitness`,
verifies the signature, ingests into the store, and `continue`s. It
does *not* surface as a `NodeEvent::Message`.

A design that wired only one seam would pass a two-node test and fail
the six-node test: a subject that comes online while a witness is
still in `run_discovery_phase` would contribute nothing to the store,
and a node with only seams 1 and 3 would still compute `Pending` for
its own KT.

**Behavior change (naming it).** Today `announce_witness` falls
through and surfaces as `NodeEvent::Message`. After seam 3 it will
not. An application that was parsing `NodeEvent::Message` for
`announce_witness` stops seeing it. This is intended, but it is a
change to the observable surface.

## §2.5 — The ClaimLog (decision)

The 6-hour first-seen rule and the trust policy's TOFU pinning both
depend on the same fact: "when did this node first observe a Key
Claim for `peer`." Today that fact lives inside `TrustPolicy`'s
`StoredClaim`. §13.7's responder semantics make it a dependency of
the witness store too, which would couple the two subsystems if the
store read `TrustPolicy` directly.

**Decision: hoist the fact into its own handle, `ClaimLog`, owned by
`Node` alongside the `DhtHandle` and `DiscoveryHandle`.**

```rust
pub struct ClaimLog {
    inner: Mutex<BTreeMap<NodeId, Timestamp>>,
}

impl ClaimLog {
    /// Record the first time this node observed `peer`'s claim.
    /// Idempotent: a later observation does not move the timestamp.
    pub fn observe(&self, peer: NodeId, now: Timestamp);

    /// When this node first observed `peer`'s claim, if ever.
    pub fn first_seen(&self, peer: &NodeId) -> Option<Timestamp>;
}
```

`Node::bind_with_store` constructs one and clones it into the trust
policy and the witness store.

**Why a shared handle and not a direct dependency.**

- Trust policy stays trust-only. It does not need to know that
  witnesses exist.
- Witness store stays witness-only. It does not need to know what
  `Trusted` or `Revoked` mean.
- One source of truth. §5.3.3's rule is a single fact; it should
  have a single home.

**What changes in `trust.rs`.** `StoredClaim.first_seen` **stays a
field** — it is part of the public shape. It is populated from the
`ClaimLog` on `observe_claim`: the policy calls
`claim_log.observe(peer, now)` (first write wins; later observations
are no-ops) and stores `first_seen = claim_log.first_seen(&peer)` in
the `StoredClaim`. So the `ClaimLog` is the single writer of the
fact and the `StoredClaim` is a cached copy refreshed on every
observation. The public shape is unchanged: the field remains, and
its value now has one writer.

**What 6a does not do with the `ClaimLog`.** It does not enforce
anything at ingest. The 6-hour rule is applied at *query* time in
`statements_for`, so a statement from a recently-seen witness is
stored (it may become useful in six hours) and filtered on retrieval.

## §3 — The responder

§13.7 is precise about the responder's job. `LookupResponse.values`
is `[* bytes]` — opaque encoded `WitnessStatement`s, not a typed
shape the responder assembles. The requester decodes them and
applies its *own* `4+ independent, first-seen 6+ hours ago,
valid_until in the future` rule. The responder does not filter to 4,
does not decide `Verified`, and does not know the requester's trust
policy.

So `respond_to_lookup` becomes:

1. Decode the `coral_lookup`'s key into a subject `NodeId`. The key
   for a Key-Claim lookup is the subject's `NodeId`.
2. Call `WitnessStore::statements_for(subject, &claim_log, now)`.
3. Encode each returned `WitnessStatement` into its QUIP-CBOR form
   and place the encoded bytes in `values`.
4. Compute `value_hash`. The response carries **one shared `values`
   blob** and one `PathProof` per path; there is no per-path value
   list on the wire. So the hash of that single returned blob is
   written into **every** path proof. A future revision that wanted
   per-path values would have to change the wire shape; 6a does not.

Today the code zeroes `value_hash`; the fix is to hash the encoded
value blob once and copy that hash into each `PathProof`.

The cap is `WITNESS_COUNT` (7 today). §13.7 does not fix a cap; 7 is
what the spec's own ring size implies.

**The responder does not filter by the requester's trust policy.**
Even if the node holds a statement from a witness the requester would
reject, the responder returns it. The requester's trust policy is the
requester's; the responder's only job is to say what it holds.

## §4 — Issuance policy (placeholder) and the spec gap

The draft specifies that a witness re-issues its statement **every
12 hours**, and §5.3.3's first-seen rule implies a witness's
statement only counts after the witness's own claim has been seen
for 6+ hours by the recipient. Neither clause says what triggers the
*first* issuance.

That is a genuine spec gap. It is recorded in the CHANGELOG's Spec
section as a new item. 6a does not invent a protocol-level answer;
it uses a node-local placeholder policy that is clearly labelled as
such:

> **Placeholder issuance policy.** A node issues a
> `WitnessStatement` about `subject` when (a) the node has a
> `StoredClaim` for `subject`, (b) the claim's `TrustPolicy` level is
> `Trusted` — the only level the policy itself can set; `Verified` is
> derived by the flow — and (c) no statement about `subject` has been
> issued by this node in the last 12 hours. The issuance time
> recorded in the statement is the current time; the recipient
> applies the 6-hour rule to that time, not the issuer.

The 6-hour rule is therefore always the *recipient's* rule, applied
to `WitnessStore::statements_for`. This matches §5.3.3's wording
("first seen" is the observer's clock) and avoids a design where the
issuer's clock has to be trusted for a threshold the issuer controls.

**Enumerating subjects.** `maybe_issue` needs the list of subjects
the policy accepts, which `TrustPolicy` does not currently expose.
6a adds `TrustPolicy::trusted_peers() -> Vec<NodeId>` (the set of
peers at `Trusted` or `Verified`). `maybe_issue` iterates that list.

Where the policy lives: `witness.rs`, as `WitnessStore::maybe_issue`
called from the peer task's steady loop every iteration; the 12-hour
cadence is enforced *inside* `maybe_issue` (it checks the
last-issued time), so the loop's call frequency does not matter. It
emits an `announce_witness` on T0.

The policy is documented in the CHANGELOG as a placeholder. The spec
pass, whenever it happens, either adopts the policy or replaces it.

## §5 — Acceptance test

Two tests in `quip-node/src/lib.rs`, using the `MeshHarness`. The
harness cap is `MESH_MAX_NODES = 6`, and the tests need all six — see
the node-count note.

**Direction.** To assert that a verifier's view of a peer `P` is
`Verified`, there must be **4 other nodes** — excluding the verifier
and `P` — that trust `P`, hold `P`'s claim past the first-seen
window, and issue statements *about* `P`. In an N=6 mesh with the
subject as verifier: `P = node 1`, `subject = node 2`, issuers =
`{3, 4, 5, 6}` — exactly four. Any other node as verifier is
symmetric by relabelling. (An earlier draft had the four witnesses
trust the *subject*, which produces statements *about the subject*
and cannot satisfy an assertion about the *subject's view*; the
setup and the assertion must point the same way.)

**Node count.** In a mesh of N, a verifier's candidate witnesses for
a peer number **N − 2** (excluding the verifier and the subject).
`Verified` needs 4, so **N ≥ 6**. The harness cap of 6 is exactly
enough; the test must not use fewer. This assumes the verifier's
*own* statement does not count — which it must not, per §5.3.3's
"independent". 6a states that rule explicitly: `compute_kt_status`
counts distinct witness NodeIds and **excludes the local NodeId**, so
a node cannot corroborate itself.

**`six_nodes_reach_verified_after_first_seen_window`**

1. Build a 6-node mesh (`MeshHarness::new(6)`).
2. Connect all; wait for all to reach `Ready`.
3. On nodes `{3, 4, 5, 6}`, call `trust_peer(node_1, Trusted)`.
4. Advance every node's `ManualClock` past
   `WITNESS_FIRST_SEEN_SECONDS + 12h` — past the 6-hour first-seen
   window *and* past one re-issuance interval, so the issuance policy
   fires at least once.
5. Each node's steady loop calls `maybe_issue`, so nodes `{3, 4, 5,
   6}` each issue a statement about node 1, and node 2 ingests them
   (seam 3) into its `WitnessStore`.
6. **Reconnect the subject to node 1.** `Ready` fires once, at
   establishment, before step 4; the flow is not advanced afterwards,
   so the subject's original `Ready` is fixed at `Pending`.
   Re-establishing runs a fresh flow whose discovery phase issues a
   new `coral_lookup` for node 1, receives the four statements (via
   the responder and seam 2), and computes `Verified`.
7. Assert the subject's new `Ready` for node 1 is
   `KtStatus::Verified`.

**Wall-clock deadline.** Step 6's re-establishment runs
`run_discovery_phase`, whose deadline is `DISCOVERY_WAIT_MS` measured
with `std::time::Instant` — real time, not the injected `ManualClock`.
So the reconnection must resolve within that wall-clock window even
though the injected clock is ~18h ahead. On loopback the lookup
resolves in well under the deadline; the test just must not advance
the clock and then block on something else.

**`six_nodes_stay_pending_before_first_seen_window`**

Same setup; advance the clocks to `WITNESS_FIRST_SEEN_SECONDS − 1s`
only; reconnect; assert the subject's `Ready` for node 1 is
`KtStatus::Pending`. This is the control: it proves the 6-hour rule
is live, not that the test happens to pass.

Both tests use the same mesh-shape helper.

**What the tests do not do.** They do not exercise trust bootstrap:
nodes `{3, 4, 5, 6}` start out trusting node 1 because the test says
so. Bootstrapping trust in a network with no prior trust is deferred.

## §6 — Out of scope, deferred, and recorded

- **Trust bootstrap.** How a fresh node acquires its first witness
  statement in a network that has none. Needs its own note.
- **Cluster-info exchange and split execution.** Deferred from
  M9.5b-c part 7. Separate note.
- **Spec item — initial witness issuance.** The draft does not
  specify it; 6a uses the placeholder in §4. Recorded in the
  CHANGELOG's Spec section, not invented here.
- **Spec item — verifier independence.** That a verifier's own
  statement cannot count toward its own `Verified` is implied by
  §5.3.3's "independent" but not stated. 6a encodes it
  (`compute_kt_status` excludes the local NodeId). Recorded in the
  CHANGELOG's Spec section.
- **Re-issuance timing.** 12 hours, per the draft. Lives as a
  constant `WITNESS_REISSUE_INTERVAL_SECONDS`.
- **TrustPolicy semantics.** Unchanged. The `ClaimLog` write path in
  `observe_claim` and the `trusted_peers()` accessor are the only
  edits; the four-level policy means exactly what it meant before.

- `quip-net/src/establishment.rs` — `compute_kt_status` excludes the
  local NodeId (verifier independence).

- `CHANGELOG.md` — new "M9.6a" section, status-table row, the

## §8 — Open questions for review

1. **Should `WitnessStore` cap total stored statements?** §13.7 does
   not say. An adversarial peer could flood the store with statements
   from witnesses it controls, subject to the per-witness 6-hour rule.
   **Answer: no cap in 6a**, a CHANGELOG note that the store is
   unbounded, and an N-Hard item to bound it. The eventual cap should
   be **per-subject**, not global, so a flood on one subject cannot
   evict legitimate statements about others. The flood is bounded to
   `(subject, witness)` pairs, which is the Sybil surface — N-Hard's
   problem, not 6a's.
2. **Should `ClaimLog` be persisted?** **Answer: in-memory in 6a**,
   with a CHANGELOG note. Persistence belongs with the store-
   persistence work M9.7 needs anyway. Note the consequence: a node
   that restarts loses its first-seen times and cannot verify (or be
   verified by) anyone for another 6 hours — which is arguably
   correct, since it genuinely has not observed those claims that
   long, but it should be stated.
3. **What does the node do with a statement it cannot verify?**
   **Resolved: `WitnessStatement::verify(&impl Verifier)` already
   exists** in `quip-core/src/messages/witness.rs` (it checks the
   witness's Ed25519 signature over `signing_payload`), and `tasks.rs`
   already imports `Ed25519Verifier`. So §7's "no `quip-net` change
   except `compute_kt_status`" holds. Each seam verifies before
   ingesting: reject on a failed signature, reject if `subject` or
   `witness` is all-zero, reject if `subject == witness`, otherwise
   ingest. Unverified statements are never stored.

## Review history

- **First review (pre-6a).** Two blocking findings, folded in:
  §1's premise about the flow's witness map was wrong (it is never
  populated in production; `Ready(Verified)` is unreachable today for
  that reason) — corrected in §1 and given its own seam, §2a seam 2;
  §5's node count, direction, and `Ready`-fires-once assumption were
  all wrong — §5 rewritten with N=6, the subject-as-verifier
  direction, and the reconnect step. Non-blocking: §2.5's "public API
  unchanged" was inaccurate (`first_seen` is a `pub` field; the fix
  keeps it and makes the `ClaimLog` its single writer), §3's per-path
  `value_hash` had no per-path values to hash (fixed to the single
  shared blob), §4 could not enumerate subjects (added
  `TrustPolicy::trusted_peers()`), §8.3 is resolved
  (`WitnessStatement::verify` exists in `quip-core`), §2a's new first
  branch changes the observable event surface (`announce_witness`
  stops surfacing as `NodeEvent::Message`), and §8.1's eventual cap
  should be per-subject rather than global.

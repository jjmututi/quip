# M9.6c — trust bootstrap

**Status:** design note. Code lands in a later commit, against this note.
The note is the contract for that commit: what a fresh node does to acquire
its first witness statements, and what the record says the alternative is.

**Scope.** Trust bootstrap: how a fresh node acquires its first corroborating
`WitnessStatement`s in a network that has none. M9.6a made `Ready(Verified)`
reachable for a node that is already inside a network of four independent,
first-seen-matured witnesses; M9.6c is the step before it. It does not change
the witness store, the claim log, or the trust policy's four-level model — it
feeds the store the first statements, and it gives the trust policy the first
peers to trust.

**Out of scope, explicitly.** The peer address book (M9.8) — how a node finds
a peer to dial is not how it decides whom to trust, and the two are separate
milestones. The issuance policy's final form (M9.6a's placeholder is
unchanged; M9.6c calls it, it does not replace it). FROST. The record names no
further exclusions; this note adds none.

---

## §1 — The decision: a configured witness ring is the trust anchor

A fresh node bootstraps trust from a configured witness ring, and the
configuration is the operator's assertion of trust, not the protocol's. Three
readings are possible, and the note names them before choosing:

1. **Configured ring.** The operator writes down the NodeIds of a witness
   ring — the `witness_ring` field M9.7's config already parses — and the node
   treats those peers as trusted-at-start for the purpose of accepting their
   statements. The node does not verify they are a ring; the operator's
   assertion is the trust anchor. This is the SSH `known_hosts` model applied
   to a ring.
2. **Discovery.** The node uses Coral to find a ring, with no
   pre-configuration, and treats the first quorum of ring-shaped peers it
   finds as its bootstrap. No operator action; the attack surface is whoever
   answers first.
3. **Hybrid.** Configured ring if present; discovery as a fallback.

**The note chooses (1).** Reading (1) is the only one where the bootstrap's
trust anchor is a decision a human made. Reading (2) has the property that a
fresh node's first trusted peers are chosen by whoever answers a Coral lookup
first, which is the Sybil surface the trust layer exists to reduce; a
bootstrap that hands the choice to the network undoes the layer above it.
Reading (3) is (2) with a config path for operators who already understand
(1), and the fallback makes (2)'s weakness the default. If a deployment has
no configured ring, the node runs at `Unknown` — which is exactly what M9.7's
production mode already does — and that is a correct state, not a failed
bootstrap.

What (1) costs, stated plainly: a node with no operator is a node that cannot
bootstrap, and that is the point. The record's own statement of the problem is

> so a fresh node needs either a configured witness ring or a discovery path
> to one. That is M9.6c's scope.

(`CHANGELOG.md:2016`–`:2018`). This note narrows that "either" to the
configured arm, and the narrowing is the decision: the discovery arm is
precisely the one whose anchor is whoever answers first. So the note does not
satisfy the record's sentence as written; it amends the second disjunct, and
the amendment is the content of the decision.

The draft makes the same point from the other side, in the one sentence a
bootstrap note has to answer:

> Without out-of-band verification, the witness ring cannot rescue a poisoned
> bootstrap.

(`draft-mututi-quip-03.xml:5362`–`:5363`). A configured ring *is* the
out-of-band verification that sentence asks for: the operator's file is
outside the protocol's trust graph, written before the node runs, and not
something an answering peer can supply.

## §1a — What the configured ring does at boot

The node reads `witness_ring` from config and validates each entry as a
32-byte NodeId. M9.7 already does exactly this: `Config::resolve` iterates the
section at `quip-node-headless/src/config.rs:224`–`:229` and calls
`decode_hex_node_id` (defined at `:281`) for every entry, warning at `:228`
that "witness_ring is parsed but not yet honoured; M9.6c consumes it". The
validation is shape-only, and it is the parser's, not this note's.
The `Trusted` decision is a second step, and the measurement constrains when
it can happen. `TrustPolicy::record_decision(&mut self, peer: &NodeId,
decision: PeerTrust, now: Timestamp) -> bool`
(`quip-node/src/trust.rs:194`) returns **false** for a peer with no stored
claim — its body ends:

```rust
match self.claims.get_mut(peer) {
    Some(stored) => { stored.trust = decision; stored.decided_at = Some(now); true }
    None => false,
}
```

So the seed cannot be applied at load time against an empty policy: every
entry would return `false` and the ring would be silently unseeded, which is
the uncalled-code class arriving as a config feature. The seed is applied at
first contact instead — after `TrustPolicy::observe_claim` (`:141`) has
inserted the peer's `StoredClaim` — and `record_decision` then returns `true`.
The code commit's test for this is not "the ring is in the config" but "a ring
member's first `observe_claim` reports `Trusted`".

Once a peer is accepted, M9.6a's issuance policy runs from the trusted set:

```rust
pub fn maybe_issue(&self, trust: &TrustPolicy, now: Timestamp) -> Vec<NodeId>
```

(`quip-node/src/witness.rs:214`), whose first act is `trust.trusted_peers()`.
The node issues statements about its peers, the statements are ingested
(`WitnessStore::ingest`, `:89`), and `Verified` follows after the first-seen
window exactly as M9.6a measured it.

A witness ring entry is trusted, not verified. The record calls the policy
"four-level" (`docs/M9.6a-design.md:407`: "the four-level policy means exactly
what it meant before"), and the enum it names has five variants — the fifth is
a tombstone, which is why the shorthand survived:

```rust
pub enum PeerTrust {          // quip-node/src/trust.rs:34
    Unknown,                  // a valid Key Claim seen for the first time
    Trusted,                  // the application has explicitly accepted it
    Verified,                 // 4+ independent witnesses corroborated it
    Untrusted,                // claim differs from the pinned one, or denied
    Revoked,                  // a revocation tombstone; terminal
}
```

The bootstrap's job is `Trusted`; `Verified` is what the statements produce. A
bootstrap that produced `Verified` directly would skip §5.3.3's first-seen
rule — "Each witness's Key Claim must have been first seen 6+ hours ago"
(`draft-mututi-quip-03.xml:1232`) — which is the rule the whole witness layer
rests on.

## §1b — The trust chain's second step

A configured ring is the anchor for *whom* to trust. What the node trusts
*about* a peer is the peer's Key Claim, and a Key Claim is a signed object the
peer presents when it connects. The bootstrap therefore does two things, and
the note separates them:

- it seeds the trust policy with the ring's NodeIds at `Trusted` —
  `record_decision(&peer, PeerTrust::Trusted, now)`
  (`quip-node/src/trust.rs:194`), which the §1a measurement places at first
  contact rather than at load;
- it accepts the ring members' Key Claims on first contact without the TOFU
  prompt an unconfigured peer gets — `observe_claim(&mut self, claim:
  KeyClaim, now: Timestamp) -> PeerTrust` (`:141`), which records the claim
  and its first-seen time in the `ClaimLog` before any early return.

`observe_claim` returns the stored trust for a known peer, `Untrusted` when a
re-observed claim differs from the stored one, and `Revoked` for a tombstoned
peer. Those three outcomes are the whole of the second step: a ring member's
claim is accepted because the config decision is already recorded, an unlisted
peer's claim is accepted as `Unknown` and waits for the application, and a
claim that differs from the pinned one is `Untrusted` for a ring member
exactly as for any other peer.

## §2 — What the note does not change

The witness store, the claim log, the issuance policy's placeholder form, and
the four-level trust policy are unchanged. M9.6c adds the seed, not the
machinery.

M9.6a's §8 answer on `ClaimLog` persistence is inherited, not closed:

> Should `ClaimLog` be persisted? **Answer: in-memory in 6a**, with a CHANGELOG
> note. Persistence belongs with the store-persistence work M9.7 needs anyway.
> Note the consequence: a node that restarts loses its first-seen times and
> cannot verify (or be verified by) anyone for another 6 hours — which is
> arguably correct, since it genuinely has not observed those claims that
> long, but it should be stated.

(`docs/M9.6a-design.md:46`–`:52`.)

The premise of that answer no longer holds as written. M9.7 landed (`e378baf`)
and gave the binary a `FileBlobStore` behind `store_path`; it did not persist
the `ClaimLog`. `bind_with_store` still constructs `ClaimLog::new()` in memory
(`quip-node/src/lib.rs:540`) and `ClaimLog` offers no serialisation at all —
its public surface is `new`, `observe`, `first_seen`, `len`, `is_empty`
(`quip-node/src/claim_log.rs:30`–`:62`). So the deferral M9.6a handed to
"M9.7's store-persistence work" is now unowned: M9.6c inherits it and does not
close it, and the consequence M9.6a named — a restarted node cannot verify
anyone for six hours — is the state the tree is in today.

## §3 — The tests that will prove it

Two tests, one per class.

- `configured_ring_seeds_trusted_peers` in
  `quip-node-headless/tests/trust.rs` — a config file carrying a
  `witness_ring` produces a node whose policy reports `Trusted` for each entry
  at that entry's first contact, before any statement has been exchanged; an
  unlisted peer still reports `Unknown`.
- `configured_ring_reaches_verified_after_first_seen_window` in the same file
  — the M9.6a shape with the ring supplied by config instead of by
  `trust_peer`: build the mesh, advance every clock past
  `WITNESS_FIRST_SEEN_SECONDS + 12h`, reconnect the subject, and assert the
  subject's `Ready` is `KtStatus::Verified`.

The M9.6a tests these mirror are
`six_nodes_reach_verified_after_first_seen_window`
(`quip-node/src/lib.rs:2286`) and
`six_nodes_stay_pending_before_first_seen_window` (`:2323`), both on the
`six_node_mesh()` harness (`:2256`). They cannot be reused as they stand: their
step 3 is "On nodes `{3, 4, 5, 6}`, call `trust_peer(node_1, Trusted)`"
(`docs/M9.6a-design.md:32`), which is precisely the call M9.6c replaces with a
config seed. The harness is reusable; the tests are copies with that one step
replaced, and the second one keeps its control shape (advance to
`WITNESS_FIRST_SEEN_SECONDS − 1s` and assert `Pending`) so the 6-hour rule is
still shown to be live.

## §6 — Open questions for review

1. **Is a configured ring authenticated at all?** The note's reading: no — the
   operator's assertion is the anchor, and requiring each entry to present a
   signed claim before it is trusted would be the same bootstrap problem one
   layer down. The alternative reading: the ring's entries sign their own
   config entry, so a tampered config is detectable. What would change the
   note's mind: if the config file's integrity is not protected at the operator
   level. Measured state: the tree protects the *seed* file and not the config
   file — `read_seed_file` (`quip-node-headless/src/config.rs:285`) reads the
   mode via `std::os::unix::fs::PermissionsExt` (`:288`), masks it `& 0o777`
   (`:293`) and rejects `mode & 0o077 != 0` (`:294`). Nothing checks the mode
   of the file that carries `witness_ring`. The note's reading stands, with
   that asymmetry recorded: an operator who protects the seed file and not the
   config file has protected the wrong half of the pair.
2. **Does a bootstrapped ring replace the TOFU prompt or precede it?** The
   note's reading: precede it. A ring member is `Trusted` on first contact; a
   non-ring peer is `Unknown` and awaits the application's decision, unchanged
   from M10.3. The alternative: the ring's presence converts the whole node
   from TOFU to "trust the ring, trust its members' statements, but not its
   members as peers" — a finer distinction than the five-variant enum carries,
   since `PeerTrust` has no state for "trusted as a witness, not as a peer".
   The note takes precede-it, because it needs no new state.
3. **What happens if the configured ring is empty?** The note's reading: the
   node runs at `Unknown` trust and is not broken; it is a node whose operator
   has not yet decided whom to trust, and that is exactly M9.7's
   production-mode state. The alternative: refuse to bind without a ring, on
   the theory that a production node without trust configuration is a
   misconfiguration. Measured state: M9.7's parser **accepts** an empty ring —
   the loop at `quip-node-headless/src/config.rs:224`–`:229` iterates whatever
   the section holds and warns; there is no emptiness check, so
   `witness_ring = []` and an absent section behave identically. The note's
   reading matches the code; refusing to bind would be a behaviour change this
   note does not ask for.

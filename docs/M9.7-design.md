# M9.7 — headless binary, configuration, and the dev/production split

**Status:** design note. Code lands in the immediately following commit,
not a later milestone. The note is the contract the code commit
satisfies.

**Scope.** A `quip-node-headless` binary that runs a QUIC node without
Flutter, a configuration file that selects between development and
production modes, structured logging, and graceful shutdown. It does not
add protocol behaviour: the binary is a caller of `quip-node`'s public
API.

---

## §1 — The decision: two modes, selected by config, not by feature flag

One binary serves both a two-node loopback test and a VPS deployment; the
difference is the configuration file, not the build. Two modes,
`Development` and `Production`, selected by the config's `mode` field. A
compile-time feature was rejected: one binary is simpler to build, and a
mode that cannot be switched without rebuilding is the mode that gets
misconfigured on the VPS.

| Field | `Development` | `Production` |
|---|---|---|
| `bind` | `127.0.0.1:0` if absent | required, no default |
| `seed` | literal 32-byte hex, or generated-and-logged if absent | required; must be a file path with permissions 0600 checked at load, never a literal |
| `store_path` | in-memory (`MemoryBlobStore`) if absent | required path to a `FileBlobStore` |
| `capabilities` | `NodeConfig::new`'s default | parsed from a `[capabilities]` section and validated with `Capabilities::new_checked` (row 4) |
| `auto_serve_pins` | `true` | required, no default |
| `relay_capable` | `false` | required, no default |
| `force_relay` | `false` | default `false`, overridable |
| `witness_ring` | absent | optional; absent means "dev-mode-like trust" and is a recorded limitation (see §4) |

A `[trust]` section in Production carries the trust bootstrap config
M9.6c will consume; in M9.7 it is parsed, validated, and **not yet
consumed** — the note states this, the code rejects an unknown key and
accepts a known-but-unused one with a `warn!`.

The modes differ this way for one reason each. Dev mode must work from a
single `cargo run` with no setup, because it is the mode a new
contributor uses and the mode every test uses; production mode must fail
closed on every security-relevant field, because it is the mode a VPS
runs unattended.

## §2 — The decision: `quip-node-headless` is a new workspace member

The binary lives in a new crate, `quip-node-headless`, added to the
workspace members list. Rejected: a `[[bin]]` target inside `quip-node`.
The binary needs `clap`/`serde`/`toml`; making them `quip-node`
dependencies would pull them into every library consumer. The workspace's
existing shape is "one crate per role"; a binary is a role.

The crate's dependency list is exactly: `quip-node`, `quip-core`,
`quip-net`, `quip-storage`, `clap` (derive), `serde` (derive), `toml`,
`tracing`, `tracing-subscriber`, `tokio` (full). Nothing else. Any
additional dependency is a decision for a later commit.

## §4 — What it defers, with the reason

- **Trust bootstrap (M9.6c).** A production-mode node is `Unknown` to
  every peer at startup and stays that way until the application trusts.
  The `[trust]` section is parsed but not consumed. The consequence,
  stated plainly: **a production deployment cannot reach `Verified` trust
  until M9.6c lands.** The record's ordering ("M9.7 after M9.6c") is
  reversed by this note, and the reversal is a scope cut, not a claim
  that the trust problem is solved: dev mode is functional, production
  mode runs and serves but at `Unknown` trust. This is recorded as the
  reason M9.6c remains a blocking item for a *real* production
  deployment, not for M9.7's code.
- **Peer address book (M9.8).** The binary has no bootstrap-peer dialling
  beyond a `[[peers]]` list; a production node that starts with an empty
  list has no way to find peers.
- **Platform signer shim (M10.4/M10.5).** The binary's seed is an Ed25519
  seed from a file or from the dev literal. A hardware-backed signer is
  not in scope.
- **Metrics/observability beyond logs.** No Prometheus, no health
  endpoint; `tracing` only.
- **Config hot-reload.** Load once, at startup.

## §5 — The tests the code commit adds

Two tests, one per class:

- `config_rejects_unknown_capability` in `tests/config.rs` — a config
  file that names a capability the code does not implement is rejected by
  `Capabilities::new_checked`, the error names the capability, and the
  node does not bind. This is row 4's closure test.
- `binary_starts_connects_serves_and_shuts_down` in `tests/binary.rs` —
  the binary binds from a dev-mode config, a second in-process node
  connects, the second sends a `get` and receives it, the binary receives
  ctrl-c and exits with code 0, and the peer task is aborted by the
  `Drop`.

A `--check-config <path>` flag on the binary parses and validates a
config file without binding; `tests/config.rs` uses it for the rejection
case so the test does not bind a socket.

## §6 — Open questions for review

1. **Should `--check-config` be a subcommand or a flag?** Flag
   (`--check-config PATH`) is simpler and consistent with `--config`.
2. **Should the dev-mode seed be generated-and-logged or
   rejected-if-absent?** Generated-and-logged: `[dev] no seed configured;
   generated <hex>, this node's identity is not stable across restarts`.
   A dev node that restarts with a new identity is exactly what a dev
   node should do; a dev node that requires a seed file is not the mode a
   new contributor can run.
3. **Should `[trust]` be parsed-and-warned or rejected outright?**
   Parsed-and-warned: the section is the M9.6c surface, and rejecting it
   would make the config file incompatible across the two milestones for
   no gain.
4. **Should the binary include `quip-node-ffi`?** No: the FFI crate is
   `cdylib`-shaped, and the binary is a direct caller of `quip-node`.
5. **Should logging be JSON in production and human in dev, or JSON
   always?** JSON in production (a VPS's log shipper wants it), human in
   dev (a contributor's terminal does not). One `if mode` in `log.rs`.

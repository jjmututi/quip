# M9.6b — cluster merge design

**Status:** design contract; revised in `3fbee08` to resolve the bf520fe review findings. No code yet; the merge code lands in M9.6b.

**Revision <SHA>:** rule 1 of §2a changed from the δ-size
trigger to the frame's proximity trigger (D7); rules 2–4 unchanged.

This note fixes the contract for cluster merging (§13.4). It exists
because row 7 of the conformance matrix is the only remaining
`review required` row: `ClusterState::should_merge` returns a
`MergeDecision` and no production code calls it, and the draft says
what a merge decision looks like without saying how a cluster gets to
one, who is allowed to propose it, what happens to the cluster id, or
what the observable completion is. A merge cannot be implemented
against the current draft because the draft does not define the
behaviour that an implementation must conform to.

The note is a contract, not a specification. It says what M9.6b will
implement, what it depends on, what it defers, and what the test
proves. It does not touch the draft's §13.4 text, which is unchanged
by this milestone; it records what the implementation does against the
draft's current wording and what follow-up the draft needs.

---

## §1 — What exists

`quip-net/src/cluster.rs` has:

- `ClusterState::should_merge(&self, now, cfg) -> MergeDecision`,
  which compares a peer's advertised cluster size against the local
  size and returns `MergeDecision::Merge { into }`, `Stay`, or
  `CreateNew`.
- `MergeDecision::Merge { into: ClusterId }` names the cluster the
  local node should join.
- The merge decision reads `size` and `id` from `ClusterInfo`
  records, which are exchanged by `cluster_info` and recorded in
  `NeighbourClusters` by `observe_cluster_info`.
- `ClusterState::migrate` moves the local node to a new cluster id;
  the split path uses it.

`quip-node/src/cluster.rs` has `ClusterHandle::plan_split` and
`split_if_due`, which drive the split path. There is no equivalent
`plan_merge` or `merge_if_due`. `should_merge` is exercised by unit
tests in `quip-net` and by nothing else.

The draft's §13.4 says (§13.4, "Cluster Merging"): a cluster may merge
into another when the smaller is at most `1/4` the size of the larger,
the merge lowers the average RTT, and the members of the smaller
cluster agree to join. It does not say who initiates, what evidence
the larger cluster requires, how concurrent merges are ordered, or
what completion means.

## §2 — The four decisions

### §2a — Eligibility: when may a merge happen?

The draft's size condition is necessary and not sufficient. The
implementation will require all of:

Rules 1 and 3, and the "no pending split / no merge in flight"
condition, are enforced by
`ClusterState::merge_proposal_eligible`. Rule 2 is enforced by the
caller, `ClusterHandle::plan_merge`, because it needs two RTT
sample sets the state machine does not hold. Rule 4 is enforced
transitively by the §13.2 acceptance test. The note records this
split so a reader can tell which code path each rule lives on.

1. **Proximity.** Eligibility's trigger is proximity, not a size ratio. The
   Coral DHT's proximity rule is the trigger: when two clusters are within
   the DHT's proximity threshold, they are close enough for one to propose a
   merge to the other. Proximity is measured by the DHT's own metric, which
   §13 already defines; the note does not introduce a second metric. This is
   the frame's D7: the trigger is proximity; the conditions this note
   defines — the RTT rule (§2a, rule 2), no pending split (§2a, rule 3), and
   level (§2a, rule 4) — are unchanged and remain in force. The decision
   function is unchanged: `ClusterState::should_merge` returns
   `MergeDecision::Merge` for the peer's `ClusterInfo`, evaluated at the
   current time and configuration.
2. **RTT.** The merge lowers the merged cluster's p90 RTT: the local
   cluster's p90 against its own members (over at least
   `ACCEPTANCE_MIN_SAMPLES`) is strictly greater than the local
   cluster's p90 against the peer cluster's members (also over at
   least 20 reachable samples). The peer cluster's members come from
   `NeighbourClusters` and the routing table. A peer cluster with
   fewer than 20 reachable members is not merge-eligible in either
   direction. This is a local measurement; it does not depend on a
   peer-advertised RTT field, because `ClusterInfo` has no such
   field and the split path's `rtt_to_center` is the same local
   measurement.
   **Enforcement.** Rule 2 is the caller's check, not the state
   machine's. `ClusterHandle::plan_merge` (the production caller,
   landing in the next commit) computes the two p90 values and
   compares them; `ClusterState::merge_proposal_eligible` does not
   take samples and cannot evaluate rule 2. The 20-sample floor and
   the local-p90 threshold are already enforced by
   `ClusterState::is_acceptable`; the peer-side p90 comparison is
   the caller's addition.
3. **No pending split.** A cluster whose `pending_split` is `Some` is
   not eligible to merge; it is already in the middle of an episode
   and the split must conclude first.
4. **Same level (enforced transitively).** The level distinction is
   not carried on the wire: `ClusterInfo` has `{id, size, ctime}`
   and no level, and `ClusterState::merge_proposal_eligible` has
   nothing to compare. A cluster at a different level cannot be
   merge-eligible for the same reason a cluster at the same level
   with a different threshold cannot be: the §13.2 acceptance test
   compares the peer's p90 against the local cluster's threshold,
   and a cluster whose members are all within a different level's
   threshold will fail the local threshold as a consequence of the
   RTT rule. `MergeRejectReason::Level` remains on the wire for a
   future in which the peer's level is carried explicitly; today
   nothing emits it. If that field is added later, rule 4 becomes a
   direct check and the `Level` reason becomes reachable.

### §2b — Authority: who initiates, and what evidence is required?

The **smaller cluster initiates.** The larger cluster accepts, rejects,
or ignores. Concretely:

- The smaller cluster's **coordinator** proposes the merge. A merge
  proposal is a new wire verb, `cluster_merge_propose`, carrying the
  proposer's `ring_id`-equivalent cluster id, the proposer's `size`,
  the proposer's `state_digest`, and a proposer signature. It is
  broadcast to the larger cluster's coordinator only.
- The **larger cluster's coordinator** decides whether to accept. The
  acceptance criteria are: the size condition (re-checked against its
  own `size` at the time of acceptance), the level match, and its
  own `ClusterState` not being in a pending split. If it accepts, it
  broadcasts `cluster_merge_accept` to its own members and to the
  proposing coordinator. The larger cluster's members do not change id;
  they are already in the surviving cluster. The proposing coordinator
  broadcasts the accept to its own members, who update their cluster id
  to the **larger** cluster's id and start announcing it through
  `cluster_info`. The larger cluster's id survives; the smaller
  cluster's id is abandoned.
- A **merge proposal must be signed by the proposer's coordinator**
  and must carry the proposer's `cluster_id` and `size`. The larger
  cluster's coordinator verifies the signature and does not need any
  other evidence. A proposal from a non-coordinator is rejected.
- If the larger cluster's coordinator rejects, it responds
  `cluster_merge_reject` with a one-byte reason code (size, level,
  busy, signature). The smaller cluster's coordinator does not
  retry within the same split/merge episode.

**Why coordinator and not each member.** A merge that required each
smaller-cluster member to accept independently would be an N-way
agreement and would need its own consensus round. The draft's §13.4
does not describe one, and the split path does not have one either: a
split is unilateral, and a merge is its dual. The coordinator is the
single proposer, and the larger cluster's coordinator is the single
accepter. Any member can dispute a coordinator decision the same way
it disputes any other coordinator action in the cluster, which is not
part of M9.6b.

### §2c — Safety: concurrent merges, stale information, and the merge id

Three cases.

**Concurrent merge proposals from two smaller clusters.** Both
proposers may target the same larger cluster at the same time. The
larger cluster's coordinator accepts the first proposal that arrives,
broadcasts acceptance, and rejects the second with reason `busy`. The
rejected proposer's coordinator records the rejection and does not
retry in the same episode.

The larger cluster's coordinator holds at most one outstanding merge
proposal at a time, in a receiver-side `PendingMerge { proposer_id,
proposed_at }` slot; a second proposal while that slot is occupied is
rejected with reason `busy`. The proposer-side `PendingMerge { target,
proposed_at }` in `ClusterState` records the proposal the smaller
cluster has in flight; the two slots are distinct and both exist for the
merge episode's duration.

**Stale `size` information.** The larger cluster's coordinator
re-checks the size condition against its own `size` at acceptance
time, not at proposal time. If the condition no longer holds — because
the larger cluster shrank between the proposal and the acceptance —
the proposal is rejected with `size`. The smaller cluster's
coordinator does not rely on its own cached copy of the larger
cluster's `size` for the acceptance decision; the coordinator's
acceptance is authoritative.

**The merge id.** The surviving `cluster_id` is the larger cluster's,
not the smaller's. The smaller cluster's members migrate to it.
`migrate` already sets a new id; the merge path calls it with the
larger cluster's id instead of a fresh one. This is the same call the
split path makes with a `JoinNear` or `JoinFar` target, and it
preserves the invariant that a cluster id names the cluster's
`Coordinator`-chosen identity, not a hash of the members.

### §2d — Completion: what is observable, and what happens on failure?

**Completion.** The merge is complete when a majority of the smaller
cluster's members *reachable at the time of acceptance* have announced
the larger cluster's id through `cluster_info`. Reachability at
acceptance is the set of smaller-cluster members the smaller cluster's
coordinator could observe in its `NeighbourClusters` record at the
moment the accept was received; members that were already `Closing` or
`Failed` at that moment are not counted. The coordinator observes the
announce through its own `NeighbourClusters`: when more than half of
that reachable set have `info.id` equal to the larger id, the merge is
complete and the coordinator emits `ClusterEvent::Merged { into:
larger_id }`. It then resets its own state: the `pending_merge` field is
cleared, the split-attempt counter is reset (a merge is not a failed
split), and the coordinator steps down in favour of the larger cluster's
coordinator on the next `elect_coordinator` interval. A member that was
unreachable at acceptance and later returns still announcing the smaller
id is excluded from the merged cluster's routing by
`is_cluster_member`'s id filter — the same treatment a member that never
migrated receives.

**Failure.** Three failure modes.

1. **Rejection by the larger cluster's coordinator.** No state change;
   the proposal is recorded as rejected and not retried in the same
   episode.
2. **Timeout.** If a majority of the smaller cluster's members have
   not announced the larger id within
   `MERGE_PROPOSAL_TIMEOUT = 3 * CLUSTER_HEARTBEAT` (180 s), the
   proposal is abandoned. The coordinator does not retry within the
   same episode; the local cluster keeps its current id and continues
   as it was.
3. **Partial migration.** A smaller-cluster member that is `Closing` or
   `Failed` at acceptance is not counted in the completion denominator
   (§2d "Completion"). The merge completes on the reachable-at-acceptance
   majority. The unreachable member is treated as having left the
   cluster; it does not block completion and is not a failure. This is a
   completion rule, not a failure mode.

## §3 — What lands in M9.6b

- `quip-net/src/cluster.rs`:
  - `ClusterState::pending_merge: Option<PendingMerge>` with
    `PendingMerge { target: ClusterId, proposed_at: Timestamp }`.
  - `ClusterState::merge_proposal_eligible(&self, peer_info,
    local_samples, now, cfg) -> bool` — the four eligibility
    conditions of §2a in one function.
  - `ClusterState::start_merge_proposal(&mut self, target, now)` and
    `ClusterState::note_merge_result(&mut self, accepted: bool,
    now)` — the pending-merge lifecycle, symmetric to the
    pending-split lifecycle.
  - `ClusterState::pending_merge_settled(&self, now, cfg) -> bool` and
    `ClusterState::note_merge_complete(&mut self, now)` — the
    completion and timeout edges.
- `quip-node/src/cluster.rs`:
  - `ClusterHandle::plan_merge(&self, dht, now) -> Option<MergePlan>`
    — reads the `NeighbourClusters` records, evaluates eligibility
    against each candidate, and returns the best eligible target.
  - `ClusterHandle::merge_if_due(&self, dht, now)` — the production
    caller that `should_merge` and `plan_merge` currently lack.
    It starts a pending merge, or concludes one, on the same cadence
    the split path uses.
    `merge_if_due` calls `ClusterState::should_merge` for each
    candidate in `NeighbourClusters` (per §2a rule 1), applies the
    caller-side eligibility conditions (§2a rules 2–3), and, if a
    candidate is eligible and no `PendingMerge` is outstanding,
    starts a merge proposal and broadcasts `cluster_merge_propose`.
    This is the caller `should_merge` currently lacks; after the
    merge code lands, `should_merge` is no longer uncalled.
  - `ClusterHandle::note_merge_result` — called by the peer task when
    the larger cluster's coordinator accepts or rejects.
- `ClusterHandle::plan_merge` evaluates rule 1 (via
  `ClusterState::should_merge`), rule 2 (via two p90 comparisons
  the handle computes), and rule 3 (via the split path's
  `pending_split` slot). It does not re-check rule 4; the
  acceptance test's threshold does that transitively. It calls
  `ClusterState::merge_proposal_eligible` only for the "no merge
  in flight" condition, which the state machine already knows.
- `quip-net/src/cluster_wire.rs` (new) or an addition to
  `cluster_info`'s codec module:
  - `ClusterMergePropose` and `ClusterMergeAccept` /
    `ClusterMergeReject` wire messages, signed by the coordinator.
  - `Message::ClusterMergePropose`, `ClusterMergeAccept`,
    `ClusterMergeReject` variants and their encode/decode dispatch.
- `quip-node/src/tasks.rs`: the `classify_inbound` function gains
  three verbs; the router sends the propose to the coordinator's
  candidate, and the accept/reject to the peer task that proposed.
- `quip-node/src/lib.rs`: `Node::cluster()` and `Node::cluster_view()`
  report `pending_merge` alongside `split_due` in `ClusterView`.
- The draft's §13.4 is unchanged by this milestone. The note records
  what the implementation does; a follow-up `docs:` commit can fold
  the four decisions of §2 into the draft.

## §4 — What the test proves

One integration test, `merge_produces_larger_cluster_id`, in
`quip-node/src/cluster.rs`:

1. Builds a `wide_mesh()` with 25 routing-eligible peers, so the
   §13.2 sample minimum is satisfiable.
2. Splits into two clusters by making the RTT samples diverge — the
   `the_cap_is_reachable_after_the_settle_interval` test already
   builds the two-cluster shape.
3. Grows one cluster to 20 members and keeps the other at 5, so the
   size condition `5 * 4 <= 20` holds.
4. Makes the smaller cluster's p90 RTT exceed the larger cluster's
   advertised class by enough that the condition holds.
5. Drives `merge_if_due` on the smaller cluster's coordinator until
   `ClusterEvent::Merged { into: larger_id }` fires.
6. Asserts the smaller cluster's members now announce `larger_id`,
   that the smaller coordinator's `pending_merge` is `None`, and that
   the split-attempt counter is 0.

Three unit tests in `quip-net/src/cluster.rs`:

- `merge_requires_the_size_condition` — a 5-member cluster cannot
  merge into a 19-member one (`5 * 4 > 19`).
- `merge_requires_enough_rtt_samples` — a cluster with fewer than
  `ACCEPTANCE_MIN_SAMPLES` is ineligible in both directions.
- `merge_rejected_when_pending_split` — a cluster with
  `pending_split.is_some()` rejects every proposal until the split
  settles.

The unit tests prove the eligibility conditions in isolation; the
integration test proves the completion.

**What the tests do not prove.** That a hostile larger cluster cannot
ignore the size condition and force a merge — the larger cluster's
coordinator re-checks the condition, but a malicious coordinator
could accept unconditionally and there is no protocol-level enforcement
short of each smaller-cluster member validating the accept message
against its own view of the larger cluster's size. That check is
deferred (see §5).

## §5 — Deliberately not in this commit

- **Per-member acceptance.** A merge that every smaller-cluster
  member independently validates against its own `NeighbourClusters`
  view would close the "hostile coordinator accepts unconditionally"
  gap. It is a larger protocol change (a merge is N-way agreement,
  not coordinator-to-coordinator) and needs its own note.
- **Cross-level merges.** §2a restricts merges to the same
  `ClusterLevel`. A merge across levels is a different operation;
  the draft's §13.4 does not describe it and this note does not
  invent it.
- **Merge retries.** A rejected merge is not retried in the same
  episode. A retry policy (exponential backoff, a cap on consecutive
  rejections) is deferred.
- **The draft's §13.4 text.** The four decisions of §2 are this
  milestone's contract, not the draft's. A follow-up `docs:` commit
  folds them into §13.4; until it lands, the draft and the
  implementation diverge in the same way row 7 already records, and
  row 7's `Specification status` stays `incomplete` until the
  follow-up lands.
- **A row in the conformance matrix for the merge wire verbs.** Row 7
  is the merge row and this note is the design for it; the wire
  verbs will get their own row when the code lands, if the matrix
  pass surfaces the need.

## §6 — What the matrix does with this note

Row 7 currently reads `FAIL` / `incomplete` / `review required`. After
the merge code lands, the row becomes `PASS` / `incomplete` /
`review required` — the code satisfies the note, but the draft's
§13.4 still does not record the four decisions. A `docs:` follow-up
that folds §2 into the draft moves the row to `PASS` / `clear` /
`non-blocking`, which is the state that closes the decisive query.

The note's §2 is the draft's next §13.4 edit. It is written to be
transcribed rather than paraphrased, so the follow-up commit is
transcription, not decision.

Edits 3–6 of the note's second revision resolved the §2b/§2c/§2d
contradictions and the undefined inputs (the peer-advertised RTT rule,
the migration trigger, the completion denominator) that made the
first revision untranscribable. The follow-up `docs:` commit transcribes
the resolved §2.

The decisive query's answer after this note's design is applied (before
the draft follow-up): still one row, `review required`, §13.4 merge.
This note does not put a code path behind the row — the merge code
lands in M9.6b. What the note does is remove the reason the row is
`incomplete`: after the note fix, the row's specification status
becomes a documentation gap rather than an undefined behaviour,
because §2 now states the four decisions the draft's §13.4 does not.
